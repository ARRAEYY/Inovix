## 3. Architectural principles (from spec §2)

1. **Two apps, one repo** — `apps/frontend/` + `apps/backend/` + shared `packages/validation/`. The validation package is a workspace dep so both apps import the exact same Zod schemas (frontend form validation + backend body validation).
2. **Backend is the security boundary.** Frontend hides UI by role but every backend route enforces RBAC independently. Never trust a request body or a frontend payment-success callback.
3. **Database is the source of truth.** Realtime events reflect persisted state; if the event and the DB disagree, the DB wins. Realtime is never used to skip persistence.
4. **Payment provider handles money; backend verifies it.** No order's Payment.status moves to `PAID` until the Razorpay webhook confirms payment. The frontend "payment success" callback is verified but not trusted — the webhook is the source of truth.
5. **Images use Cloudinary with signed uploads from backend; frontend never holds Cloudinary credentials.**
6. **Build and test incrementally.** Every milestone ends in a working demo. No big-bang integration.

## 4. Authentication model

### 4.1 Token lifecycle (spec §3.2 Layer 1)

- **Access token**: JWT, 15 min TTL, signed with `JWT_SECRET`
- **Refresh token**: opaque random 48-byte value (sha256-hashed in DB), 7-day TTL, **rotating**
- **On logout**: refresh token is revoked (set `revokedAt`)
- **On suspend**: all refresh tokens for the user are revoked immediately

### 4.2 Refresh token rotation

Each refresh token can be used exactly once. Using it issues a new access + new refresh, and marks the old refresh as `replacedBy=<newTokenId>`. Re-using an already-rotated refresh is treated as a token-theft event: **all of the user's refresh tokens are revoked**, forcing a re-login.

### 4.3 RBAC enforcement layers (spec §3.2)

1. **JWT claims** — `{ sub, email, role, outletId, exp }` in the access token
2. **Express middleware** (3 composable guards):
   - `protect` — verifies JWT, looks up the live user record (so role/status changes take effect immediately), attaches `req.user`
   - `authorizeRole(...roles)` — checks `req.user.role ∈ roles`; 403 otherwise
   - `requireOutletScope` — for outlet-scoped routes, ensures `req.user.outletId` is set
3. **Prisma row-level filters** — every outlet-scoped Prisma query includes `where: { outletId }`. Enforced in the repository layer.
4. **Frontend UI hiding** — sidebar items, action buttons, route guards all keyed off the JWT claims. This is convenience, not security.

## 5. Order state machine (spec §8.6)

```
                ┌──────────────────────────────────────────────┐
                │                                              │
                ▼                                              │
  PENDING ──► ACCEPTED ──► PREPARING ──► READY ──► COMPLETED  │
    │           │              │           │                   │
    │           │              │           └─► CANCELLED        │
    │           │              │              (no refund —      │
    │           │              │               student no-show)│
    │           └──────────────┴─────────────► CANCELLED        │
    │                                          (full refund)    │
    └─► REJECTED (full refund)                                  │
                                                                │
  Terminal states: COMPLETED, REJECTED, CANCELLED ◄────────────┘
```

**Refund implications** (handled by `payments.service.processAutoRefundOnTransition`):

| Transition              | Refund? | Trigger                |
|-------------------------|---------|------------------------|
| PENDING → REJECTED      | Yes     | `OUTLET_REJECT`        |
| PENDING → CANCELLED     | Yes     | `CUSTOMER_CANCEL` / `OUTLET_CANCEL` |
| ACCEPTED → CANCELLED    | Yes     | `OUTLET_CANCEL`        |
| PREPARING → CANCELLED   | Yes     | `OUTLET_CANCEL`        |
| READY → CANCELLED       | NO      | (no-show / timeout; food wasted) |
| READY → COMPLETED       | NO      | (student picked up)    |

**Student Cancellation**: Students are allowed to cancel an order **only while it is in the `PENDING` state** (before outlet acceptance) via `POST /api/v1/orders/:orderId/cancel`, which triggers an automatic full refund (`CUSTOMER_CANCEL`). Once an order reaches `ACCEPTED` or beyond, student cancellation is disabled and returns `400 INVALID_TRANSITION`. Only outlet staff/admin can cancel after acceptance.

## 6. Realtime strategy (spec §6.2)

### 6.1 Events

The backend emits exactly three Socket.IO events (per spec):

| Event                       | Rooms                          | Emitted from                          |
|-----------------------------|--------------------------------|---------------------------------------|
| `order:new`                 | `outlet:<outletId>`            | payments.service after webhook confirms payment |
| `order:status:changed`      | `outlet:<outletId>` + `student:<userId>` | orders.controller.updateOrderStatus |
| `notification:created`      | `user:<userId>`                | notifications.service.createForOrder |

### 6.2 Critical: events fire AFTER DB commits

Per spec §2 principle 3: "Realtime events reflect persisted state; the DB is the source of truth." If the DB write fails, no event is emitted. The event is a side-channel for UX; the client can always re-fetch via REST.

### 6.3 Long-polling fallback (spec §11 risk matrix)

College networks that block WebSocket upgrades during exam week silently downgrade to HTTP long-polling — this is automatic via the `transports: ['websocket', 'polling']` option in `src/lib/socket.js`. The client's TanStack Query cache invalidates on socket events OR on a 30-second REST polling fallback (frontend responsibility).

### 6.4 Client auth

The frontend passes the access token via the `auth` field of `io.connect()`:

```js
import { io } from 'socket.io-client';
const socket = io('http://localhost:3000', {
  auth: { token: localStorage.getItem('accessToken') },
  transports: ['websocket', 'polling'],
});
```

The server middleware verifies the token, joins the user to `user:<id>`, `outlet:<outletId>` (if outlet staff), and `super-admin` (if super admin) rooms.

## 7. Payment model (spec §1.2)

Each outlet owns and operates its own Razorpay account. The platform never touches money.

```
1. Student creates Order → status=PENDING, Payment.status=PENDING
2. POST /api/v1/payments/razorpay/order
     → Backend decrypts outlet's stored Razorpay credentials
     → Creates Razorpay Order at gateway
     → Returns gateway order id + outlet's public keyId
3. Frontend shows Razorpay Checkout
4. POST /api/v1/payments/razorpay/verify
     → Backend recomputes HMAC-SHA256 over (razorpayOrderId + "|" + razorpayPaymentId)
       using the outlet's keySecret (decrypted)
     → Compares in constant time with the provided signature
     → On match: Payment.status=PAID, emit `order:new` to outlet
5. (Parallel) Razorpay calls POST /api/v1/payments/razorpay/webhook
     → Backend verifies webhook signature using outlet's webhookSecret
     → Idempotent: if Payment.status already PAID, ack and return
```

### 7.1 Encrypted credential storage

Outlet credentials are stored encrypted at rest in the `Outlet` table:

| Field                       | Encryption                              |
|-----------------------------|-----------------------------------------|
| `razorpayKeyIdEnc`          | AES-256-GCM (iv:tag:ciphertext, base64) |
| `razorpayKeySecretEnc`      | AES-256-GCM                             |
| `razorpayWebhookSecretEnc`  | AES-256-GCM                             |

The encryption key is `OUTLET_CREDENTIALS_KEY` — **separate from `JWT_SECRET`** per spec §4 entity #4. Set it via `openssl rand -base64 32` and store in your secret manager (never commit).

Super admin sets the credentials via:

```
POST /api/v1/payments/admin/outlets/:outletId/razorpay-credentials
{ "keyId": "...", "keySecret": "...", "webhookSecret": "..." }
```

## 8. Audit log (spec §4 entity #19)

Every state-changing outlet/admin operation writes an `AuditLog` row via the `audit()` helper in `src/lib/audit.js`. The helper is fire-and-forget — a failure to write the audit log must never break the request it is recording.

Schema:
```
AuditLog {
  id, actorUserId?, action, targetType, targetId?,
  before (JSON), after (JSON),
  ip, userAgent, createdAt
}
```

Retention: 90 days rolling via the `audit-purge` cron (see `docs/cron.md`).

## 9. Logging & error handling

### 9.1 Centralized error envelope (spec §5)

```json
// Success
{ "success": true, "data": { ... }, "meta": { "page": 1, "pageSize": 20, "total": 137 } }

// Error
{ "success": false, "message": "...", "code": "OUTLET_CLOSED", "errors": [] }
```

### 9.2 Production safety

- `helmet` sets security headers
- 10 KB body size cap on JSON requests
- `express-rate-limit` — 200 req/min/IP general, 20 req/15 min on `/api/v1/auth`
- 500 errors don't leak internal messages in production (`NODE_ENV=production`)
- The Razorpay webhook route uses `express.raw({ type: 'application/json' })` because the signature is computed over the raw body — JSON parsing happens after signature verification.

## 10. Dev environment

- **DB**: SQLite (file: `apps/backend/dev.db`) — zero setup
- **Provider swap to Postgres**: change `provider = "sqlite"` → `"postgresql"` in `prisma/schema.prisma`, set `DATABASE_URL=postgresql://...` in `.env`, run `npx prisma migrate dev`
- **Seed**: `npm run db:seed` (idempotent; safe to re-run)
- **Run**: `npm run dev:backend` (uses `node --watch` for hot reload)
- **Tests**: `npm run test --workspace=backend`
- **Studio**: `npm run db:studio` (Prisma Studio at localhost:5555)
